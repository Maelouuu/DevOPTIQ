Les fondations

Architecture

DevOPTIQ est une application web Flask déployée sur Google Cloud Run. Elle suit le pattern Application Factory : la fonction create_app() dans Code/app.py configure l'ensemble de l'application puis enregistre tous les blueprints. Chaque domaine fonctionnel est isolé dans son propre blueprint.

Vue d'ensemble de l'infrastructure DevOPTIQ

Flux de démarrage

Au démarrage du conteneur (serveur WSGI gunicorn, config unifiée gunicorn.conf.py), create_app() exécute dans l'ordre :

  1. Configuration DB (PostgreSQL si DATABASE_URL présent, sinon SQLite local), pool configurable via DB_POOL_SIZE/DB_MAX_OVERFLOW
  2. Configuration Flask-Mail (mail 100 % par variables d'env — désactivé proprement si non configuré, flag MAIL_CONFIGURED)
  3. Enregistrement des ~49 blueprints (dont les 7 blueprints Refonte Compétences V1.1)
  4. db.create_all() + ajout colonnes manquantes via ALTER TABLE idempotent (_safe_add_column) + marquage Alembic — protégé par lock_timeout : une migration ne peut plus bloquer le démarrage
  5. Réinitialisation du pool de connexions DB avant d'accepter les requêtes HTTP
  6. Init console serveur (Code/logstream.py — tee stdout/stderr vers un fichier plafonné 2 Mo, hors tests)

Gestion des fichiers sur Cloud Run

Cloud Run utilise un filesystem éphémère. DevOPTIQ contourne ce problème en persistant les données critiques en base : Entity.svg_content (SVG cartographie), Entity.optiqcarto_data (état JSON éditeur), FileBlob (pièces jointes).

Authentification

Blueprint : auth_bp — fichier : Code/routes/connexion_routes.py

Authentification email/mot de passe, sessions Flask côté serveur uniquement (pas de JWT).

Flux de connexion

  1. POST /login — vérifie l'email, valide le hash avec check_password_hash()
  2. Si valide : stocke session['user_email'] et session['user_id'], redirige vers /activities/map
  3. Si invalide : flash() d'erreur, retour au formulaire
RouteMéthodeDescription
/loginGET, POSTFormulaire de connexion
/logoutGETEfface user_email, user_id, active_entity_id de la session
/auth/current_user_infoGETInfos utilisateur connecté en JSON (id, prénom, nom, rôles, manager)

Sécurité

  • Mots de passe : politique centralisée dans Code/security.py — hash_password() / verify_password() / needs_rehash(). Standard = PBKDF2-SHA256 600 000 itérations (OWASP). Ne jamais appeler generate_password_hash directement.
  • Rétro-compatibilité : les anciens hashes (scrypt Werkzeug 3, ~162 caractères) restent acceptés au login et sont re-hachés silencieusement vers le standard. Migration idempotente au démarrage : users.password élargi à VARCHAR(255).
  • Fiabilité : set_password et le reset par email relisent le hash en base après commit — jamais de faux succès.
  • Clé session : variable d'environnement SECRET_KEY (branche distribution : plus de défaut public — secret éphémère + warning si absente)
  • Reset password : blueprint auth_password_bp (routes_password.py)

Patterns de contrôle d'accès

# Pattern 1 — vérification user_id
user_id = session.get('user_id')
if not user_id:
    return redirect(url_for('auth.login'))

# Pattern 2 — vérification email (cartography_editor)
def _require_auth():
    return bool(session.get("user_email"))
Pas de décorateur @login_required centralisé — chaque blueprint vérifie la session indépendamment.

« champion » a changé de sens

Le mot désignait l'ARBITRE ; c'est désormais le coordinateur. is_coordinator_status() reconnaît donc tous les libellés historiques de l'arbitre (manager, « Gestionnaire de compétences », sa troncature à 20 caractères, « Competency Manager ») : users.status est un texte libre, écrit différemment selon les instances. migrer_anciens_champions() tourne au démarrage — et ne se joue qu'une fois (marqueur statuts_quatre_paliers en base). Rejouée à chaque démarrage, elle promouvait coordinateur tout champion créé depuis : le nouveau palier n'existait que jusqu'au prochain redéploiement.

Ce que chaque palier ouvre se RÈGLE

L'échelle est la grammaire du produit et ne bouge pas. Ce qu'elle ouvre se règle, parce qu'une entreprise n'a pas les mêmes usages qu'une autre : une matrice de 7 droits × 4 paliers, dans la page Comptes (GET|POST /comptes/droits). Le branchement est unique — DROITS_DEFAUT, droits_effectifs() et a_le_droit(droit, user) dans Code/permissions.py ; tous les can_* y délèguent.

  • Le tableau par défaut EST le comportement d'hier. Une instance qui n'a jamais rien réglé ne change pas de comportement en prenant ce code — sans cette règle, une livraison redistribuerait silencieusement les droits de tout le monde.
  • On ne stocke que les ÉCARTS au défaut. Enregistrer la table entière figerait les valeurs d'origine : le jour où le produit en change une, les instances qui n'y avaient jamais touché garderaient l'ancienne sans le savoir.
  • La colonne admin est verrouillée à vrai, et le serveur la reforce. Se retirer les Paramètres, ce serait perdre l'écran depuis lequel on les remettrait.
  • Seul un administrateur écrit ce tableau ; un coordinateur le lit. Un coordinateur qui pourrait s'attribuer les sections d'administration s'attribuerait la clé IA de l'entreprise.
  • Aucun cache dans flask.g. g vit aussi longtemps que le CONTEXTE, pas la requête : la suite de tests garde un contexte applicatif ouvert du début à la fin, si bien que le premier réglage lu y restait figé pour toute la session.

La porte d'écriture — une seule, pour toute l'application

Code/ecriture.py est un before_request qui refuse toute méthode d'écriture, sauf ce qui est nommé dans sa liste d'exemptions.

39 fichiers de routes écrivaient sans aucun contrôle d'accès

Relevé le 11/10/2026 : tasks.py (5 routes), gestion_outils.py (4), roles.py, savoirs, savoir_faires, aptitudes, softskills, constraints, propose_from_file.py, time_view.py (14)… et aucun before_request global ne les couvrait. Mesuré, porte retirée : un compte user créait une tâche et réécrivait la description d'un outil du catalogue partagé ; et POST /tasks/add SANS AUCUN COMPTE rendait 201 et écrivait la tâche en base. Corriger 39 fichiers un par un, c'est 39 occasions d'en oublier un — et surtout la quarantième route écrite demain serait ouverte à nouveau. Le défaut est donc fermé par classe.

# Le verdict, isolé de Flask — pour qu'il soit testable tel quel.
def porte(chemin, methode, en_test=False):
    if methode not in METHODES_ECRITURE:        return None
    if _hors_compte(chemin) or _exempte(chemin): return None
    if current_user() is None:
        return None if en_test else "non_connecte"
    if _peut_ecrire():                           return None
    # Avant de refuser : ce geste se PROPOSE-t-il ?
    if _peut_proposer(chemin, methode):          return VERDICT_PROPOSITION
    return "lecture_seule"
  • La liste d'exemptions est le cœur du fichier, et elle a été écrite d'après ce que la porte a RÉELLEMENT refusé en rejouant la suite (66 refus journalisés avec le statut du compte), pas d'après ce qu'on imaginait : trois familles n'avaient pas été prévues. Elle ne contient que des routes qui portent DÉJÀ une règle plus fine — /mastery, /plan, /paliers, /comptes, /gestion_rh, /cartography/api, /api/import, /api/propositions.
  • _peut_ecrire() consulte can_edit sur la carto ACTIVE, pas seulement a_le_droit('edit_carto'). Sur une carto PRIVÉE, son propriétaire fait ce qu'il veut quel que soit son statut. Mesuré avant livraison sur le pilote : deux comptes ARaymond (un champion propriétaire de sa carto, un user) auraient perdu le droit d'écrire chez eux. Une porte qui contredit la règle qu'elle fait respecter est un deuxième avis, pas une porte.
  • La règle anonyme s'efface sous TESTING, volontairement : 115 tests fabriquent des clients anonymes pour s'isoler de la session partagée, pas pour éprouver l'anonymat. Conséquence à ne pas oublier : passer la suite ne prouve PAS que l'anonyme est fermé — seul tests/test_102_porte_ecriture.py le prouve, en appelant porte() avec en_test=False.

Carto commune et accès par rôle

Relue le 19/10/2026 · Code/carto_access.py, Code/routes/carto_sharing.py

Recopier l'entité chez chacun — le modèle historique — fabriquait autant de cartos que de comptes : plus rien ne les reliait, et une correction devait être refaite sur chaque copie. Une carto commune est au contraire une seule ligne travaillée par plusieurs comptes : ce qui est validé est vu par tout le monde, il n'y a rien à propager.

ObjetRôle
Entity.is_sharedPrivée par défaut. Une carto qu'un compte crée pour lui n'obéit à rien de ce qui suit.
entity_role_access(entity_id, role_id) — on ouvre l'accès à des RÔLES, jamais à des comptes : qui reçoit le rôle demain entre sans qu'on revienne sur l'écran. Aucune ligne = ouverte à tous.
entity_status_access(entity_id, palier) — un rôle dit ce qu'on FAIT dans l'organisation, un statut ce qu'on EST dans l'application. Par défaut coordinateur et administrateur ouvrent toutes les cartos.
Entity.statuts_reglesLe premier réglage GRAVE d'abord le défaut : sans cela, décocher « coordinateur » aurait rouvert l'accès par le défaut resté implicite.

Deux pièges que chaque écran d'accès doit énoncer AVANT le clic

Une carto privée ignore les rôles (can_read rend la main au propriétaire avant même de les consulter) — la cocher la rend commune, sinon on enregistrerait un accès qui ne produit rien. Et une carto commune sans aucun rôle autorisé est ouverte à TOUS : y poser le premier rôle la RESTREINT, donc cocher peut retirer l'accès à des gens qui l'avaient.

Deux écrans, une seule table

  • La page Partage (/share) travaille UNE carto : ses rôles, leurs titulaires, sa vignette, ses propositions.
  • La matrice de la page Carte (GET|POST /cartography/api/access/matrice) regarde l'ensemble : un rôle en ligne, une carto en colonne. Deux sections dans une seule table — par statut (4 lignes fixes, toujours visibles) puis par rôle.
  • On envoie des CASES, jamais la table entière : deux personnes qui règlent l'accès en même temps s'effaceraient l'une l'autre, et une case oubliée dans l'envoi fermerait un accès que personne n'a décidé de fermer.
  • La ligne admin est verrouillée (cases disabled, et le serveur refuse de la retirer) : se décocher sur une carto qu'on ne possède pas la ferait disparaître de l'écran d'accès — il n'existerait plus aucun endroit d'où se la rendre.

BOOLEAN DEFAULT 0 a mis staging à terre

PostgreSQL refuse un entier comme défaut de booléen ; SQLite l'accepte, donc aucun test de la suite ne pouvait le voir. _safe_add_column avalant l'erreur, entities.is_shared n'était jamais créée et toute requête sur entities tombait en 500 — page Carte comprise. Écrire DEFAULT FALSE dans les ALTER, et sa.false() (jamais text('0')) en server_default de modèle. Le démarrage vérifie désormais les colonnes indispensables (_verifier_colonnes) ; tests/test_67_schema_postgres.py compile le DDL avec le dialecte PostgreSQL, sans serveur.

Ménage obligatoire. Supprimer une entité efface entity_role_access, entity_status_access, carto_change_requests, activity_change_requests et import_records : PostgreSQL applique les clés étrangères, SQLite non.

Un champion ne peut pas écrire directement sur une carto commune : il dépose, un coordinateur applique ou refuse. Ce qui est appliqué vaut pour tout le monde. Deux familles, deux mécanismes — et la raison de leur différence est structurelle.

Le chemin d'une proposition de données

1

Le gesteLa porte le détourne — 202, code: "proposition". Rien n'est écrit.

2

Le lotIl s'accumule dans un brouillon (status='draft'), relu puis envoyé.

3

L'examenMême fenêtre que les propositions de carte, même bandeau.

4

Le rejeuLes vraies routes, commits neutralisés. Tout ou rien.
  • Un LOT, pas un geste par proposition. Corriger une fiche, c'est cinq ou six clics ; une proposition par clic demanderait six décisions au coordinateur pour un seul travail — et on refuse une intention, pas une touche de clavier.
  • La porte DÉTOURNE, elle ne refuse plus. C'était le trou : can_edit rend faux pour un champion sur une carto commune, donc il se voyait opposer lecture_seule — le motif réservé à user. Il pouvait proposer une modification de la CARTE, et rien de ce qu'elle porte.
  • On ne détourne que ce qu'on saura rejouer (route_existe, plus une liste explicite de chemins). Un POST vers une URL qui n'accepte que PUT devenait une proposition — acceptée, examinée, puis impossible à appliquer.
  • Côté écran, on enveloppe fetch plutôt que les huit fichiers JS de la page Activités : chacun lit sa réponse à sa façon, et le neuvième écrit demain passerait à côté. La réponse est clonée — un flux ne se lit qu'une fois, et l'appelant va le lire à son tour.

Tout ou rien : chaque route appelée fait son propre commit()

Rejoués tels quels, cinq gestes donnent cinq transactions : si le troisième échoue, les deux premiers sont déjà écrits et personne ne peut dire où la proposition s'est arrêtée. _neutraliser_commits() remplace commit par flush le temps du rejeu — le motif de tools/provisioning/provision.py, pour la même raison. Mesuré : un geste impossible rend 409 rejeu, 0 ligne écrite, la proposition reste pending, et l'écran dit lequel a bloqué.

La fenêtre de la page Carte remplace l'ancien « Import IA global ». Une carte par nature — rôles, tâches, outils — dans la couleur de la page où vivent ses données, plus l'import multiple (plusieurs fichiers, ou un classeur dont chaque feuille est reconnue).

L'IA désigne les COLONNES, elle n'écrit aucune donnée

Le prompt import.correspondance rend une ligne d'en-tête et un numéro de colonne par champ ; le code relit ensuite les valeurs dans le fichier. Une réponse qui porterait des lignes est ignorée, un numéro hors du fichier écarté. Une IA qui réécrirait les lignes pourrait en inventer ; une IA qui désigne des colonnes se vérifie d'un coup d'œil.

  • Le code ne devine pas. Un fichier non reconnu n'est pas lu « à moitié » : l'écran dit ce qui manque, montre le début du fichier tel quel et propose l'IA ou le modèle. Une feuille ambiguë (« Nom | Description » : des rôles ou des outils ?) n'est pas importée tant qu'on ne l'a pas dite.
  • L'import revérifie tout — rien de ce que renvoie le navigateur n'est cru, pas même le statut d'une ligne — et un import multiple s'écrit en UNE transaction, dans l'ordre rôles → outils → tâches : un rôle créé par la feuille « Rôles » existe quand une tâche le désigne comme garant.
  • Une liste de personnes est RECONNUE, jamais importée depuis la carte : créer un compte engage toute l'instance. La même fenêtre s'ouvre depuis la page Comptes avec ?pour=comptes, pour qui en a le droit.
  • L'écran se lit aussi dans l'autre sens : « Partir des activités sans tâches » pose la question à l'envers (« cette activité n'a aucune tâche : laquelle de ces lignes la remplit ? ») et écrit dans le MÊME état — deux mécanismes auraient fini par dire deux choses.

Role.hors_carte — importer des rôles ne servait à rien

_sync_carto_to_db effaçait, à chaque enregistrement de la carte, tout rôle absent de ses bandes : un rôle importé, créé depuis la page RH ou désigné garant disparaissait avec ses titulaires et ses liens aux tâches. Les rôles créés hors de la carte portent désormais la marque et survivent ; reprendre_roles_hors_carte() marque UNE fois ceux qui existaient déjà.

L'historique des imports

ImportRecord (import_records), écrit par /api/import/importer dans la MÊME transaction que l'import — une trace qui survivrait à un import annulé mentirait. Une carto se remplit par petits bouts ; sans trace, « d'où vient cette tâche, et qui l'a mise là ? » n'a aucune réponse.

  • Une ligne par (dépôt, carto, nature), réunies par lot : c'est ce qui permet de dire « le même dépôt a servi à… ».
  • detail porte les libellés, pas des identifiants : l'historique doit rester lisible même si l'objet a été renommé ou supprimé depuis.
  • Rien n'est écrit quand rien n'a été ajouté : relire un fichier déjà importé est le geste le plus courant, une trace vide ferait croire à un import.
  • Lisible par qui peut OUVRIR la carto, pas seulement par qui a importé : la question se pose d'abord à celui qui trouve la tâche.

Paliers de performance

Relue le 19/10/2026 · Code/paliers.py, Code/routes/paliers_routes.py

Une sortie d'activité porte une norme chiffrée (« 48 h au plus », « 95 % au moins »). On pose des marches vers cette norme, on relève une mesure en séance, et le niveau se DÉDUIT du chiffre — il ne se coche pas.

NiveauD'où il vient
2 — qualifiéla norme est atteinte
3 — avancéle seuil « au-delà » est franchi
4 — expertisejamais déduit : il se pose à la main, et lui seul

Le niveau d'une activité est le MINIMUM de ses sorties, celui d'un rôle le minimum de ses activités, et NULL (non évalué) n'est jamais zéro.

Dépasser la norme ne faisait pas monter le niveau

pas_de_progression ne regardait que les marches EN DEÇÀ de la norme et en déduisait une marge. Reproduit au chiffre près : cibles 67 → 81 → 95 (norme) → 98, marge déduite 14, seuil au-delà à 109 % — une valeur qui n'existe pas sur un pourcentage. Une mesure à 99 % restait donc au niveau 2, alors qu'une marche avait été posée exprès à 98 %. Et « Enquête client » marchait par hasard (20 → 14 → 10 → 6 : marge 4, seuil 6, qui tombait pile sur la marche posée) — le même code rendait le bon résultat d'un côté et le mauvais de l'autre. La règle : une marche posée au-delà de la norme EST le seuil, et c'est la première. L'erreur redescendait jusqu'au verdict « apte / pas apte » par la règle du minimum.

L'écran

  • Le relief remplace l'ancien rail : deux axes réels — le TEMPS en abscisse (les séances sont à 17, 17 puis 26 jours d'écart : la dernière pente est plus douce), la valeur ordonnée par mérite en ordonnée, de sorte que monter veut toujours dire progresser, qu'il s'agisse d'une durée ou d'un taux. Le tracé est DROIT entre deux mesures : rien n'a été relevé entre les deux, une courbe lissée inventerait ce qu'on ne sait pas.
  • Évaluer est une PAGE, pas un tiroir : trois colonnes (les activités du rôle, la sortie, le contexte). Le tiroir reste pour les deux dialogues courts — configurer une activité, diagnostiquer un écart.
  • Un placeur pose les étiquettes du relief par ordre de priorité et ne dessine pas ce qui ne rentre pas : la norme, puis les mesures (la plus récente d'abord), puis les cibles. Quand la place manque, ce qui saute est la décoration, jamais le chiffre relevé.

Module Rôle — estimation par récurrence

Chaque TimeRoleLine porte une activité, une récurrence (journalier / hebdomadaire / mensuel / annuel) et une fréquence. _role_summary() calcule :

annual  = Σ(daily × freq)  × Js × Sa
          + Σ(weekly × freq) × Sa
          + Σ(monthly× freq) × 12
          + Σ(yearly × freq)
monthly = annual / 12

où Js = jours/semaine et Sa = semaines/an issus de get_calendar_params().

Blueprint : chatbot_bp — fichier : Code/routes/chatbot.py, préfixe /api/chatbot.

  3. Cloud Run staging tourne en --no-cpu-throttling : le sous-processus démarre APRÈS la réponse HTTP ; sans CPU alloué en continu il est étranglé à ~5 % et une exécution de 3 min en prend 60.

Les bancs

Chaque banc monte une instance jetable (SQLite temporaire) et SÈME le décor qu'un écran doit savoir montrer. Le principe tient en une phrase : sans les cas malheureux, on ne regarde jamais que le cas heureux.

La suite

Plus de 3 300 cas. Deux règles de fond :

  • La base ET la session sont partagées (scope=session dans conftest.py) : c'est la première cause de faux échecs. Un cas monte son propre décor et le nettoie. client et auth_client sont le MÊME objet — un test de l'anonymat fabrique son propre app.test_client().
  • tests/conftest.py retire les clés IA avant de créer l'application : des dizaines de cas vérifient le comportement sans clé et comptaient sur le fait qu'un poste de développement n'en a pas. Sur l'instance, Cloud Run les porte dans l'environnement — 15 tests rouges sur 5 fichiers, donc un taux de fiabilité faux par construction. Un contrôle qui dépend de la machine ne contrôle rien.

Le cliquet : un test se vérifie ROUGE

Un cas écrit après coup passe au vert quoi qu'il arrive. La pratique est donc de remettre le défaut un par un et de constater que le cas tombe — c'est ainsi qu'on découvre ceux qui ne mordent pas. Deux exemples réels : un cliquet qui neutralisait un garde que le chemin rendait déjà inutile (il a mis au jour un outil qui héritait d'une activité), et un autre qui cherchait data-poser-norme — présent aussi dans un sélecteur voisin, donc retirer le bouton laissait le test vert.

tools/repet_image.sh

Répète la disposition de l'image SANS Docker (exclusions du .dockerignore + purge bytecode, tests/ épargné) et y lance la suite. À passer avant toute livraison : depuis que la suite tourne sur l'instance, un test qui lit un fichier SOURCE échoue là-bas en passant ici. C'est ainsi qu'ont été trouvés les cas de test_61 (lecture de pulse/app.py), test_65 (sources de hub/), test_107 (runpy.run_path) et test_111 (Code/example.vsdx, exclu par *.vsdx). Tous portent désormais une garde de saut : un contrôle qui rougit toujours n'est plus lu, et le jour où il a raison personne ne regarde.

Écart normal entre les deux : la suite locale compte ~40 cas de plus que l'arbre d'image, tous des lectures de sources absentes de l'image.

Conventions de développement
